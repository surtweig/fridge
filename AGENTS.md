# Fridge — Technical Overview

> Status snapshot for future agent sessions. Written from a code-walkthrough of
> the repository as of the latest commit (`7f0162d`, FRIDGE_VIDEO_240X180).
> Source of truth is the code itself; treat this document as a map, not a spec.

## 1. What Fridge is

Fridge (formerly "XCM2 Fridge") is a fantasy 8-bit game console:

- **CPU**: Intel 8080 ISA, **big-endian**, extended with graphical
  instructions and an optional Posit16 math coprocessor (PAM16). 10 MHz clock.
- **RAM**: 64 KiB, 16-bit address space. Code, data, stack and the memory-mapped
  video aperture live in the same 64 KiB. The first `FRIDGE_EXECUTABLE_OFFSET`
  (0x0200) bytes are reserved for the boot loader; user executables load at
  0x0200. `FRIDGE_ASCENDING_STACK` is defined — the stack grows upward.
- **Video**: dual framebuffers plus 64 KiB sprite memory (~102 KiB total video
  RAM). Two configurable resolutions selected at compile time via
  `FRIDGE_VIDEO_240X180`:
  - 240x160 (legacy, README default; 40x20 text mode with a 6x8 font)
  - 240x180 (current build; 40x22 text mode)
  4-bit (16 entry) palette, RGB4096 source. Sprites with 8 compositing modes
  (invisible, opaque, transparent0, additive, subtractive, AND/OR/XOR).
- **ROM**: SD-card style, max 16 MiB, addressed in 256-byte segments via a
  streaming protocol driven by the boot loader.
- **Interrupts**: system timer (IRQ 0x0004), keyboard press (0x0007),
  keyboard release (0x000a). The 8259-style two-byte interrupt vector is
  emulated in `FRIDGE_cpu_interrupt`/`pcRead`.

The canonical hardware reference is `doc/specs.txt`, `doc/instructions-reference.txt`
and the IR-code enum in `include/fridge.h` (`FRIDGE_IRCODE`).

## 3. The ISA, in practice

- **Encoding**: one byte opcode, followed by 0–2 bytes of inline operand
  (`FRIDGE_INSTRUCTION_MAX_EXTRA_SIZE == 2`). Instruction order in the
  `FRIDGE_IRCODE` enum **is** the opcode value. `falc` resolves the mnemonic
  names through its static `IRIDs`/`IRSigs` maps; numeric opcodes in hand-written
  assembly are written as `#JMP` etc.
- **Big-endian**: 16-bit data is stored and read high-byte-first
  (`FRIDGE_DWORD_HL`, `pcReadDouble` push H then L). This is the most notable
  divergence from real i8080 documentation and a common source of bugs.
- **Registers**: A, B, C, D, E, H, L, F (flags) plus 16-bit pairs
  BC/DE/HL/SP/AF. The M operand denotes `memory[HL]`.
- **Flags** in `rF` (`FRIDGE_FLAG_*_MASK`): Sign 0x80, Zero 0x40, **Panic 0x20**
  (Fridge-specific — set by `corePanic` to halt the CPU on stack corruption),
  Aux 0x10, Parity 0x04, Carry 0x01. Note: the parity-flag implementation in
  `defaultSetFlags`/`compareSetFlags` carries TODOs and does **not** match the
  i8080 spec (uses even/odd instead of even-parity-of-low-byte).
- **Fridge-specific additions** beyond stock 8080:
  - `MVI_M`, `LDAX_HL`, `STAX_HL`, `MOV_*M`, `DAI` (decimal adjust
    immediate / posit-related), `HLSP` (load HL from SP), `RTC`, `IIN`/`IOUT`
    (renamed IN/OUT).
  - **Video instructions**: `VPRE`, `VMODE`, `VPAL`, `VFSA`, `VFSI`, `VFSAC`,
    `VFLA`, `VFLAC`, `VS2F`, `VSSA`, `VSSI`, `VSLA`, `VSS`, `VSD`. They talk
    directly to the GPU through `FRIDGE_CPU::gpubus`.
  - **PAM16** (`PAM16C`): single opcode dispatching to a Posit16 coprocessor
    command selected by the low nibble of A (see `FRIDGE_PAM16_COMMAND`).
- **Reserved opcode space**: `IR247`..`IR255` are placeholders unless
  `FRIDGE_POSIT16_SUPPORT` is defined, in which case 247 becomes `PAM16C`.

## 4. Emulator core (`fridgemulib/`)

Pure C89-ish, single translation unit (`fridgemulib.c`) with no platform
dependencies beyond `<string.h>`-style stdlib. Driven by `FRIDGE_sys_tick(sys)`,
which advances the CPU by one instruction. The host application (test bench, Qt
GUI, the future WASM runtime, …) calls it in a loop.

- `FRIDGE_cpu_reset` zeroes registers and loads the boot image. `SP` defaults to
  `0xFFFF` unless `FRIDGE_ASCENDING_STACK`, in which case code paths initialise
  `0x1000` (see the test bench).
- `corePanic()` sets the Panic flag and halts the CPU; this is the only trampoline
  out of the run loop besides `HLT`.
- GPU: `FRIDGE_gpu_render_ega_rgb8` and `FRIDGE_gpu_render_txt_rgb8` produce an
  RGB888 host-side framebuffer; `..._area` variants render a sub-rectangle
  (used by the Qt frontend for incremental updates).
- ROM: emulates the SD-card protocol — segment select, mode byte, streaming
  bytes via `IN`/`OUT` to `FRIDGE_DEV_ROM_ID`, with interrupt signalling when a
  block is ready. See `fridge-boot/BootLoader/BootLoader.x2al` for the canonical
  handshake.
- Keyboard: 32-deep ring buffer; `FRIDGE_keyboard_press`/`_release` enqueue
  events that the CPU consumes via IRQs.

The test bench in `fridgemulib/main.cpp` is the project's de facto regression
suite. It exhaustively tests every `MOV_*` register pair and runs 100 iterations
of `PUSH`/`POP` for each register pair. `fridge_emulator_autotests/` contains a
Qt Test (`tst_fridgemulib_tests.cpp`) covering Posit16 bit-ops, pack, float
conversion, add/mul/div — it is referenced by the `.pro` system and not yet
ported to CMake.

Currently only `fridgemulib` builds under Linux; `build/fridgemulib` is the
test-bench binary.

## 5. Toolchain

- **falc** (`falc/`): the active assembler. Two-pass: parse → resolve
  aliases/includes/entries/subroutines → address markup → codegen. Supports
  `include`, `alias`, `static` data, `subroutine`/`endsub`, `entry`, `offset`,
  `unsafe_flow`, an optional `-vhdl` mode that emits a VHDL ROM initialiser.
  Standard library lives in `x2al_std/` (e.g. `vtext.inc` text-mode helpers,
  `arithm.inc` 8x8→16 multiplication, `posit.inc` PAM16 wrappers).
- **Frion / CPM** (`emulator/cpm/`, surfaced via the `frion/` VS Code ext):
  a Lisp-influenced higher-level language with namespaces, structs, statics,
  `if`/`for`, function calls, and an explicit **intermediate representation**
  (see `doc/cpm-intermediate.txt`, `CPMIntermediate.{h,cpp}`). Codegen emits
  Fridge Assembly, which is then run through falc. **Status: "In progress"** —
  parser and intermediate emit work, assignment operators and static-symbols
  via INDEX/REF syntax nodes were the most recently active areas
  (commits `25dec74`, `3b0d0dc`, `7931ac7`).
- **x2al** (`emulator/x2al/`): the predecessor assembler (`XCM2AssemblyLanguage-
  Compiler.cpp`), still referenced by the Windows DirectX emulator. falc is the
  successor; do not extend x2al for new work.
- **rombuild** (`emulator/rombuild/`): packs assembled `.bin` blobs into a
  segment-indexed ROM image consumable by the SD-card protocol.
- **fridge_sdk** / **fridge_opengl_emulator**: Qt-based IDE and Qt+OpenGL host.
  `fridge_opengl_emulator.pro` pulls `falc/FridgeAssemblyLanguageCompiler.cpp`
  and `fridgemulib/fridgemulib.c` directly as sources (no shared library), so
  any change to the core immediately recompiles into the GUI.

## 6. FPGA design (`fpga/fridge_graphics_de0cv/`)

VHDL implementation of the same ISA. The CPU (`FridgeCPU.vhd`), graphics
adapter, RAM, raster font (`FridgeRasterFont.vhd`) and PAM16 coprocessor
(`FridgePAM16.vhd`, `PAM16Adder.vhd`, `PAM16Unpacker.vhd`) are all kept in source
control alongside their Quartus project files. `RAMInit.hex`/`.mif` are the
flashed boot image. **Status: "On hold"** per the README and per the project's
new direction (see §8) — kept in-tree for reference but not the active focus.

Known code-level gotchas worth flagging in any future session:

- The **parity flag** is wrong (`// TODO doesn't meet i8080 specification`).
- `falc` 与 `x2al` share a 6x8 font and IR enum but the two assemblers are
  not bit-compatible in all corner cases (anonymous labels, `#NAME` opcode
  form). falc is the canonical path going forward.
- `FRIDGE_KEYBOARD_KEY_*_MASK`, IRQ vector layout and the boot sector index at
  `FRIDGE_BOOT_SECTION_INDEX_ADDRESS` (0x0003) form an implicit ABI between
  the boot loader, ROM builder, and emulator; changing any of them is a
  cross-component change.
- `FRIDGE_VIDEO_240X180` changes framebuffer size, text-mode rows (22 vs 20),
  and several derived constants; the Windows emulator binary in-tree was built
  against the older 240x160 mode and the Qt project's hardcoded UI sizes also
  assume 160.

## 8. Direction going forward (per the project owner)

Future development is **Linux-first** and targets three execution substrates,
all of which use the existing portable C core in `fridgemulib/`:

1. **Linux native emulator.** Promote `fridgemulib/` from a test bench to a
   real host front-end (SDL2 or similar) and add CMake targets for `falc`,
   `rombuild`, and the autotest suite currently pinned to Qt Test.
2. **WebAssembly emulator.** Compile `fridgemulib.c` (and `posit.c`) with
   emscripten; expose `FRIDGE_sys_tick`, GPU render callbacks and keyboard
   enqueue via the embind/`extern "C"` surface already in `fridgemulib.h`. The
   header is already callback-clean (`FRIDGE_INPUT_CALLBACK` /
   `FRIDGE_OUTPUT_CALLBACK`), so the WASM shell should mostly be canvas +
   requestAnimationFrame glue.
3. **Bare-metal RISC-V via static binary translation.** A new translator that
   consumes assembled Fridge ROM images and emits native RISC-V machine code
   (static translation, not JIT), for execution without an OS on a RISC-V
   target. This is a green-field component; nothing in-tree implements it yet.
   Expect to share the ISA definition (`include/fridge.h`) and the falc operand
   decoder as the front end, and generate RISC-V instructions for each Fridge
   opcode with fast-paths for the hot loops.

The FPGA path (`fpga/`) and the Windows-only DirectX emulator
(`emulator/emulator/`) are **not** the focus and should be treated as legacy
reference material unless explicitly requested. New work should target
`fridgemulib/`, `falc/`, and a new translator/runtime component (likely under a
new top-level directory).

## 9. Useful commands

```bash
# Build and run the emulator-core test bench (MOV + PUSH/POP matrix)
cmake -S fridgemulib -B build && cmake --build build -j && ./build/fridgemulib

# There is no global `make`/`cmake --build` target; build each component:
cmake -S falc          -B build-falc && cmake --build build-falc -j

# Quick sanity check of the IR-code enum against the assembler:
grep -nE '^\s+[A-Z_]+,?\s*(//.*)?$' include/fridge.h | head -300
```

There are no `npm run lint` / `ruff` / `typecheck` style commands in this
repository. The closest equivalent is running the `fridgemulib` test bench
above; treat a clean run as the green build signal.
